\chapter{Alert Delivery Path and Its Verification}
\label{app:alertpath}

Supporting evidence for the alert-delivery pipeline summarised in Chapter~\ref{ch:methodology}. The board runs a continuous capture-classify loop whose hysteresis logic is a tick-for-tick Python copy of \texttt{distraction\_alert\_controller.v}. It uses the same 40\% confidence threshold, the same eight-tick set and clear counters, and the same order of set and clear checks relative to counter increments, so an ``uncertain'' low-confidence tick holds both counters steady instead of resetting them, exactly like the RTL always-block does. On the rising edge of an alert, and only then, not once per classified frame, it posts the class, confidence and the JPEG-encoded triggering frame to a FastAPI backend. This backend stores the image and serves it to a Kotlin Android client, over the same bearer-token authentication used by the rest of the API.

A fully organic end-to-end trigger needs a person to hold a distracted pose in front of the camera for roughly seventy seconds, at this board's inference speed. Because of that, verification was carried out in three independent layers instead.

\chapter{Physical Buzzer Alert Output}
\label{app:buzzer}

Supporting evidence for the buzzer paragraph in Chapter~\ref{ch:methodology}. This appendix covers why the board could not drive a buzzer at all before this work, what was built to fix that, the real problems hit along the way, and how the buzzer itself was diagnosed and driven correctly.

\section{The board could not control the header pin at all}

The available buzzer is a real two-pin passive unit, with no transistor or driver circuit to hand, so it had to be wired directly to a GPIO-capable header pin. Checking \texttt{/sys/class/gpio} on the board's stock PYNQ image showed only one exposed GPIO controller, \texttt{zynq\_gpio} (118 lines, 54 processor MIO pins plus 64 EMIO pins), and none of those lines reach the board's PMOD headers. The PMOD and LED-adjacent pins sit on FPGA-fabric I/O banks, not the processor's fixed MIO banks. No bitstream or overlay file exposing them existed anywhere on the board's filesystem. Nothing on this board could toggle a header pin from Python without a custom bitstream built specifically to expose it. This was worked out by direct inspection, not assumed.

\section{The overlay}

A minimal Vivado project was built from scratch at \texttt{fpga/vivado\_overlay\_buzzer/}, targeting \texttt{xc7z020clg484-1}, the real device on the board (distinct from the \texttt{distraction\_alert} project's Basys3 target used in Section~\ref{sec:fpga-alert-design}). The block design (Figure~\ref{fig:buzzer-bd}) consists of a Zynq7 Processing System block and a single-bit AXI GPIO block. The processing-system block does not reconfigure the processor: Linux is already running from the SD card independently of this design. It is included so Vivado generates the AXI clock, reset and address-decode plumbing that lets the already-running processor address a peripheral built in the reconfigurable fabric. The GPIO block's output was brought out to package pin V7, which the board's user guide identifies as header J62 pin 1 (\texttt{PMOD2\_0}, LVCMOS33) \citep{xilinx2019ug850}.

\RequiredFigure[0.85\textwidth]{zc702_buzzer_overlay_block_design.pdf}{The buzzer overlay's Vivado block design. A Zynq7 Processing System block provides AXI/clock/reset plumbing to the already-running processor. A single-bit AXI GPIO block is the only new circuit, exposed externally as \texttt{buzzer\_o} on package pin V7.}{fig:buzzer-bd}

Three real build errors were hit and worked through by reading Vivado's own output rather than guessed in advance. A manual clock-connection automation call errored because the AXI4 connection automation had already wired the clock. The redundant call was removed. \texttt{make\_bd\_pins\_external} does not accept a \texttt{-name} option in this Vivado version, confirmed against its own \texttt{-help} text, so the external port was renamed after creation instead. The generated wrapper Verilog file was assumed to land under a \texttt{.gen} build-products directory and was in fact under \texttt{.srcs}, so the add-files step had to be corrected. Synthesis, implementation and bitstream generation then finished with zero errors. \texttt{write\_hwdef} produced a \texttt{.hwdef} file that turned out to already be a ZIP archive containing a valid \texttt{.hwh} hardware-handoff file. This is the metadata PYNQ needs to know the GPIO block's address on the AXI bus, alongside the bitstream itself, which configures the fabric electrically but carries no address information of its own. No separate \texttt{.hdf}-to-\texttt{.hwh} conversion step was needed for this Vivado version.

\section{Root permission and two unrelated Jupyter defects}

Loading the overlay (\texttt{pynq.Overlay(...)}) initially failed with \texttt{RuntimeError: Root permission needed by the library}. This was traced to a hardcoded check in \texttt{pynq/xlnk.py} (\texttt{if os.getuid() != 0: raise RuntimeError(...)}), not a file-permission problem. Giving the \texttt{xilinx} user read and write access to \texttt{/dev/xlnk} through \texttt{udev} rules was tried first, and testing confirmed it did not fix it. The fix that actually worked was changing the \texttt{jupyter.service} systemd unit from \texttt{User=xilinx} to \texttt{User=root} and restarting the service. This is the standard PYNQ convention on Xilinx's own reference image. This particular community board image had simply been set up differently. A live kernel process owned by \texttt{root} after the change confirmed the fix worked. Two unrelated defects in the same service were found and fixed while debugging this. \texttt{HOME} was wrongly set to \texttt{/root} for every kernel the service spawned, which broke the \texttt{tflite\_runtime} import used throughout the on-device work (Section~\ref{sec:arm32-issue}), since it lives under \texttt{/home/xilinx}. The configured notebook directory had also drifted away from where the board's own notebooks actually live, hiding them from the browser's file tree. Both were fixed in the service's own startup script.

\section{Driving a passive buzzer}

Holding the GPIO pin at a steady logic level produced a single click on each transition, not a tone. This is the expected behaviour of a ``passive'' buzzer, which has no built-in oscillator and only responds to a changing voltage, unlike an active buzzer that would tone continuously under steady DC. The fix was to generate an actual square wave in software. This used a tight busy-wait loop polling the clock rather than \texttt{time.sleep()}, which produced a noticeably less jittery tone, at the cost of pinning a CPU core for the whole alert. A frequency sweep from 300~Hz to 4{,}000~Hz was used to pick 2{,}500~Hz by ear as the clearest and loudest. Some residual timing instability is inherent to generating a waveform in software on a non-real-time operating system, and this was accepted rather than chased further, since it does not affect whether the alert is actually audible.

\section{Integration}

\texttt{alert\_loop\_infer.py} lazily loads the overlay once per process and caches the GPIO pin handle, since loading an overlay is too slow to repeat on every alert. The buzzer is sounded on the same rising edge as the backend post, inside the same alert-handling branch, so the two channels never diverge. The fix was confirmed working through the real Jupyter server rather than a directly spawned kernel, since the server's own process, not a manually launched one, is what carries the corrected root permission.
