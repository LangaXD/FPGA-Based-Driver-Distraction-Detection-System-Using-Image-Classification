\chapter{Introduction}
\label{ch:introduction}

\section{Problem overview}

Distracted driving is one of the biggest causes of road traffic collisions. Texting, handheld phone use, eating and drinking, adjusting in-cabin controls and talking to passengers all pull a driver's attention away from the road for long enough to matter at speed. Camera-based monitoring is one of the most direct ways to detect this automatically, and image classification has become the standard approach, where a model learns a fixed set of distraction categories from a single camera and flags it when a driver falls into one.

The practical problem is that almost every published system, including the first phase of this project, is trained and tested under one fixed set of conditions, one camera position and one lighting environment. Such a model has not been shown to work if the camera is mounted somewhere else, or if the vehicle is driven at night, and both of these are normal in a real deployment yet neither is usually tested. A second gap follows on from this. Even a model that classifies correctly is not a usable in-vehicle system on its own, since it needs to run on hardware that could actually sit in a car, a real way of turning a classification into an alert, and real measurements of what that hardware costs, not laptop-only estimates.

\section{Current issues and the gap this project addresses}

Three gaps motivate this project. Chapter~\ref{ch:litreview} checks each one against the reviewed literature.

First, camera-view robustness is rarely tested directly. Where multi-view datasets exist, most published work uses only a single view from them, or tests within one view rather than across views. Left and right distraction classes make this worse, not better, since a front-facing camera mirrors the image compared to a side-mounted one, so a texting-left action recorded from the front looks, in pixels, like texting-right from the side, and pooling views together without correcting for this would quietly corrupt the labels.

Second, lighting robustness is talked about often and measured on real data rarely. Where night performance is looked at all, it is often approximated by adding synthetic darkening or infrared-like colour changes to daylight images, a reasonable approximation of robustness but not a substitute for real low-light footage, since it cannot reproduce what an infrared light actually does to a scene, the loss of colour information, the way skin and fabric reflect near-infrared light and the sensor noise of a camera working at its limit. This project originally planned a synthetic experiment like this and dropped it on purpose once real low-light data became available.

Third, the step from a trained model to a working alert system is usually left as a future direction rather than actually attempted. Reported frames-per-second figures are often laptop numbers, not measurements on the kind of hardware a low-cost deployment would actually use, the accuracy and size cost of quantisation is often left out, and the logic that turns noisy per-frame predictions into a stable alert is rarely specified or tested at all.

\section{Project details}

The project is built in two connected phases that match these gaps.

\textbf{Phase 1 - AI robustness.} A single-view baseline is built first. A custom CNN, MobileNetV2 and EfficientNet-B0 are trained on the State Farm Distracted Driver Detection dataset (10 classes, 22{,}424 images) using a subject-wise split, and compared on accuracy, macro F1, per-class recall and throughput. Two robustness tests are then run separately on real data. Camera-view robustness is tested by combining State Farm (side view) with SAM-DD, a separate dataset giving paired front and side views. Lighting robustness is tested by combining State Farm with the real night-time part of the Low-Light Driver Distraction Dataset \citep{saad2020lowlight}, recorded under active infrared light, measuring how far the day-only model's accuracy drops before any fix is applied.

\textbf{Phase 2 - hardware.} The fine-tuned model is quantised to INT8 TensorFlow Lite and deployed on a Xilinx ZC702 board, a Zynq-7000 device chosen because it has a general-purpose ARM Cortex-A9 core that can run a full CNN, unlike a plain FPGA with no processor on it. Real on-device latency and accuracy are measured here, not estimated. A separate decision stage implementing the hysteresis logic needed to stop a flickering alert is designed in Verilog, checked in simulation against real model predictions and synthesised for a low-cost FPGA target, and an alert path from the board to a hosted backend to an Android client closes the loop.

\section{Aims and objectives}

\begin{enumerate}[itemsep=0.15em]
	\item To prepare and use suitable driver-distraction image data, including real multi-view and real low-light data, for training and testing a camera-view-robust and lighting-robust classification system.
	\item To build and test a prototype running on real, low-cost embedded hardware, with an alert output that reacts to sustained distraction rather than a single momentary prediction and to measure the accuracy, size and latency cost of getting there.
\end{enumerate}

\section{Research questions}
\label{sec:research-questions}

\begin{enumerate}[itemsep=0.15em]
	\item[\textbf{RQ1}] How do a custom CNN, MobileNetV2 and EfficientNet-B0 compare when the test drivers are not present in the training data?
	\item[\textbf{RQ2}] How much does accuracy change when a model is tested on a different, unseen camera view and does fine-tuning on multi-view data close that gap?
	\item[\textbf{RQ3}] How much accuracy does a day-trained model lose on real infrared-illuminated footage and how much can be recovered by training on real night data rather than synthetic approximations?
	\item[\textbf{RQ4}] What does INT8 quantisation and embedded deployment cost in accuracy, model size and latency before and after conversion and how do laptop figures differ from real on-device performance?
	\item[\textbf{RQ5}] Which part of a complete pipeline, the classifier or the decision logic after it, can actually be built and checked in FPGA hardware in the time available?
\end{enumerate}

Every experiment in Chapter~\ref{ch:results} is tied to one of these questions. Section~\ref{sec:qr-rq-summary} gives the answer each one produced.

\section{Feasibility, commercial context and risk}

The scope was set around what could actually be built and measured, not just simulated. A full CNN accelerator in FPGA fabric was set aside early on as unrealistic in the time left, so the ZC702's Cortex-A9 core runs the classifier instead, with the fabric used only for the decision stage, already flagged as a fallback plan in the Interim Progress Report.

The commercial case here rests on cost, not novelty. Driver monitoring is already required in new vehicle types in several markets, but those systems are usually built in by the manufacturer. The retrofit and fleet market is different, since older vehicles, taxi and delivery fleets and driving schools are served by hardware with a much smaller budget, which is why this project targets parts costing tens of pounds, not thousands. There are risks too, drivers resisting a system that feels like surveillance, false alerts carrying liability risk, and the real distance between a research prototype and a safety-certified product, all revisited in Chapter~\ref{ch:evaluation}.

The main technical risk that actually happened during the project was a low-level mismatch between the only published TensorFlow Lite runtime for this board and its real CPU instruction set (Section~\ref{sec:arm32-issue}). Fixing it, instead of giving up on on-device inference, became one of the biggest pieces of practical work in this project.
